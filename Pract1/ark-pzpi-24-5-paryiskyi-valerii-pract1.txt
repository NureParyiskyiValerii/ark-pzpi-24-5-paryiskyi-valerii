3.1 Важливість правил оформлення коду

  Правила оформлення програмного коду (code convention) – це узгоджений набір
домовленостей про те, як записується код: як форматується текст програми, як
утворюються імена, коли й про що пишуться коментарі, як організовуються файли
проєкту. На відміну від стандарту мови, конвенція не змінює того, що код
означає, – вона визначає, як він виглядає та які конструкції вважаються
прийнятними.
  Головним обґрунтуванням потреби в конвенції є співвідношення між написанням
і читанням коду. Фрагмент програми пишеться один раз, а читається
багаторазово: під час рев’ю, налагодження, дописування суміжної
функціональності, а через тривалий час – і самим автором. Отже, оптимізувати
слід саме читання.
  Для команди розробників стандартизація означає, що весь код проєкту виглядає
так, ніби його написала одна людина. Авторство окремого фрагмента перестає
бути помітним, і це бажаний результат: читач не витрачає зусиль на адаптацію
до чергового індивідуального стилю.
  Основні переваги дотримання стилю кодування:
  – читабельність: увага читача спрямована на логіку програми, а не на
розшифровування запису;
  – підтримуваність: новий учасник команди починає працювати з кодом, а не з
розпитувань колег;
  – мінімізація помилок: частина дефектів стає неможливою ще на етапі
написання, оскільки їх забороняє конфігурація інструментів;
  – чисті зміни: у порівнянні версій (diff) видно лише змінену логіку, а не
переформатовані пробіли та перенесення рядків.
  Останній пункт має безпосередній практичний вимір. Якщо учасники команди
користуються різними налаштуваннями редактора, то зміна трьох рядків логіки
може виглядати як зміна двохсот рядків файлу. Рев’ю такої зміни перетворюється
на пошук суттєвого серед несуттєвого, а конфлікти злиття виникають там, де
змістового конфлікту не було.

3.2 Структура коду

  Структура коду охоплює організацію проєкту та файлів, логічний поділ на
модулі й класи, а також використання коментарів для структурування великих
файлів.
  Поширені два підходи до організації каталогів. Поділ за технічним шаром
групує файли за їхньою роллю (контролери, служби, моделі), поділ за
функційністю – за частиною предметної області. Другий підхід зручніший під час
супроводу: усе, що стосується однієї сутності, лежить поруч, тому зміна в
межах однієї функційності не розходиться по всьому дереву каталогів.
      1  src/
      2    tasks/
      3      task.service.ts      // бізнес-логіка роботи із задачами
      4      task.repository.ts   // доступ до сховища
      5      task.types.ts        // типи, специфічні для модуля
      6    shared/
      7      types/        // типи домену, спільні для клієнта і сервера
      8      utils/

  Окремою рекомендацією для TypeScript є винесення типів предметної області у
спільний модуль, який імпортують і клієнтська, і серверна частини. Оскільки
обидві частини посилаються на один опис домену, вони не можуть розійтися
непомітно: зміна типу одразу спричиняє помилку компіляції в усіх місцях, де
цей тип використовується.
  На рівні модулів і функцій діє принцип єдиної відповідальності: модуль
відповідає за одну частину системи, функція виконує одну дію. Практичним
критерієм перевірки є формулювання назви: якщо назву функції неможливо
вимовити без сполучника «та» («зберегти та надіслати»), то це дві функції, а
не одна.
  Орієнтовні рекомендації: функція має вміщатися на один екран без
прокручування; рівень вкладеності не перевищує трьох, а глибша вкладеність
замінюється ранньою перевіркою з негайним виходом; експорт модуля оформлюється
іменованими експортами замість експорту за замовчуванням, оскільки ім’я
іменованого експорту неможливо змінити довільно під час імпорту.
  Коментарі-роздільники доречні на рівні файлу або модуля, де вони групують
блоки спорідненого коду:
      1  // ---- Валідація вхідних даних ----
      2  export const TaskSchema = z.object({ /* ... */ });
      3
      4  // ---- Перетворення у модель домену ----
      5  export function toTask(raw: unknown): Task { /* ... */ }

  Усередині функції такий роздільник має протилежне значення: він свідчить, що
функція виконує кілька дій. У цьому випадку розділяти код слід не коментарем,
а виділенням нової функції (метод рефакторингу Extract Method).

3.3 Форматування коду

  Форматування визначає відступи, вирівнювання та довжину рядків. Конкретні
значення залежать від мови та домовленостей команди, проте важливим є не вибір
значення, а його єдність у межах проєкту.

Параметр      | Типове значення                              | Хто визначає
--------------+----------------------------------------------+--------------
Розмір        | 2 пробіли (JavaScript, TypeScript), 4        | конфігурація
відступу      | пробіли (Python, C#, Java)                   | проєкту
Довжина рядка | 80–120 символів                              | конфігурація
              |                                              | проєкту
Табуляція чи  | пробіли – у більшості мов; табуляція – у     | мова або
пробіли       | мові Go                                      | команда

  Питання «табуляція чи пробіли» має аргументи з обох боків. Ширина символу
табуляції залежить від налаштувань редактора, тому той самий файл виглядає по-
різному в різних розробників; пробіл має фіксовану ширину в будь-якому
середовищі. Протилежний аргумент полягає в тому, що саме змінна ширина
табуляції дозволяє кожному обрати зручний для себе відступ, не змінюючи файл,
– і цей аргумент покладено в основу стандартного форматера мови Go.
  На практиці суперечка розв’язується не аргументами, а конфігурацією: файл
.editorconfig задає параметри для редакторів, а форматер приводить код до
єдиного вигляду автоматично. Після цього стиль перестає бути предметом
обговорення.
  Окремо розглядається розташування фігурних дужок. Стиль K&R розміщує
відкривну дужку в тому самому рядку, що й оголошення, стиль Allman – на
наступному рядку. У більшості мов обидва стилі рівноправні, проте в JavaScript
і TypeScript вибір має наслідки для коректності програми через механізм
автоматичної вставки крапки з комою (Automatic Semicolon Insertion, ASI).
  Згідно зі специфікацією ECMAScript, після ключового слова return крапка з
комою вставляється завжди, якщо далі в тому самому рядку немає інших лексем.
Тому запис у стилі Allman дає результат, відмінний від очікуваного:
      1  function getResult()
      2  {
      3    return            // інтерпретатор вставляє тут крапку з комою
      4    {
      5      ok: true        // це вже не об’єкт, а блок коду з міткою
      6    };
      7  }
      8  // функція повертає undefined

  Синтаксично такий код коректний, тому ні компілятор, ні лінтер без
спеціального правила помилки не виявлять. Саме тому в JavaScript і TypeScript
стиль K&R є фактичним стандартом, і це рішення обґрунтоване поведінкою мови, а
не естетичними міркуваннями.

3.4 Іменування змінних, функцій та класів

  Імена є основним засобом передавання змісту в програмному коді. Конвенції
іменування визначають, який регістр застосовується до якої сутності, і цим
дозволяють розпізнавати сутність за виглядом її імені.

Стиль         | Що ним називають               | Мови
--------------+--------------------------------+-----------------------------
camelCase     | змінні, функції, методи        | JavaScript, TypeScript,
              |                                | Java, C++
PascalCase    | класи, типи, інтерфейси,       | більшість мов
              | компоненти                     |
snake_case    | змінні та функції              | Python, Ruby, C
UPPER_SNAKE_CASE | константи                      | більшість мов
kebab-case    | імена файлів, класи CSS        | вебтехнології

  Крім регістру, діють змістові принципи вибору імен:
  – зрозумілість: функція називається дієсловом, бо виконує дію; змінна –
іменником, бо зберігає значення; булеве значення починається з is, has або
should, бо відповідає на питання «так чи ні»;
  – лаконічність: ім’я містить потрібний мінімум слів – taskList, а не
listOfAllTaskObjects;
  – унікальність: імена, що відрізняються лише суфіксом (task і taskData
поруч), ускладнюють читання і призводять до помилок.
      1  // Погано
      2  const d = new Date();
      3  const list2 = f(list);
      4  let flag = true;
      5  function proc(x) { /* ... */ }
      6
      7  // Добре
      8  const createdAt = new Date();
      9  const activeTasks = filterActive(tasks);
     10  let isCompleted = true;
     11  function archiveTask(task: Task): Task { /* ... */ }

  Окремою вимогою є уникнення «магічних» чисел – числових літералів, зміст
яких не відновлюється з контексту. Магічне число приховує одразу два факти:
власне значення та спосіб його утворення. Іменована константа розкриває
обидва:
      1  // Погано
      2  if (now - task.createdAt > 86400000) { archive(task); }
      3  if (task.status === 2) { /* ... */ }
      4
      5  // Добре
      6  const DAY_MS = 24 * 60 * 60 * 1000;
      7  if (now - task.createdAt > DAY_MS) { archive(task); }
      8  if (task.status === TaskStatus.Done) { /* ... */ }

  Запис 24 * 60 * 60 * 1000 кращий за 86400000, оскільки показує не лише
значення, а й спосіб його отримання. Водночас не кожне число є магічним:
літерали 0, 1 та -1 у звичних ролях (початок масиву, інкремент, ознака «не
знайдено») імені не потребують.

3.5 Коментарі

  Коментар є єдиною частиною файлу, яка не компілюється й не перевіряється
тестами. Компілятор ніколи не повідомить, що коментар суперечить коду, тому
коментар може тихо застаріти й залишитися на екрані як хибна документація. Із
цього випливає основне правило: коментар має містити те, чого в коді немає і
не може бути.
  Коментарі поділяють на два види за призначенням. Коментар, що пояснює код,
переказує дію, уже видиму з тексту програми, і є надлишковим. Коментар, що
пояснює логіку, містить причину прийнятого рішення – інформацію, яку з коду
відновити неможливо.
      1  // Надлишковий коментар: переказує код
      2  i++;                       // збільшуємо i на 1
      3  for (const t of tasks) {}  // цикл по задачах
      4
      5  // Потрібний коментар: пояснює причину
      6  // Зовнішній API повертає дату без позначки часового поясу,
      7  // тому додаємо Z вручну, інакше дата зміститься на пояс.
      8  const iso = raw + 'Z';

  Випадки, коли коментар є обов’язковим: неочевидне рішення, яке виглядає
помилковим, але таким не є (обхід дефекту бібліотеки, вимога замовника);
зовнішнє обмеження (формат чужого API, ліміт запитів); тимчасове придушення
перевірки компілятора.
  Останній випадок у TypeScript має власну конвенцію. Директиви @ts-expect-
error і @ts-ignore обидві придушують помилку наступного рядка, проте @ts-
expect-error сам стає помилкою, якщо помилки вже немає. Отже, він сам
усувається, коли причина зникає, тоді як @ts-ignore залишається назавжди і
може приховати вже іншу помилку. Тому рекомендованою є перша директива,
обов’язково з коментарем про причину.
  Надлишкових коментарів уникають не оновленням, а видаленням: якщо коментар
переказує код, його слід прибрати, а не підтримувати в актуальному стані. Якщо
ж код незрозумілий без коментаря, то першою спробою має бути покращення імен і
виділення функції, і лише потім – додавання коментаря.

3.6 Документування коду

  Документаційний коментар – це коментар спеціального формату, з якого
інструмент генерує довідку, а середовище розробки показує підказку при
наведенні на виклик. Звичайний рядковий коментар такої ролі не виконує.

Інструмент | Мова       | Формат
-----------+------------+--------------------------------------------------
Javadoc    | Java       | блок /** */ з тегами @param, @return, @throws
Doxygen    | C++, C, C# | блок /** */ з тегами @brief, @param, @return
JSDoc      | JavaScript | блок /** */; типи зазначаються в самому коментарі
TSDoc      | TypeScript | блок /** */; типи беруться із сигнатури
docstring  | Python     | рядок у тілі функції; стандарт PEP 257

  Структура документаційного коментаря включає стислий опис призначення, опис
параметрів, значення, що повертається, перелік винятків та, за потреби,
приклад використання:
      1  /**
      2   * Архівує задачу та прибирає її зі списку активних.
      3   *
      4   * @param task - задача, яку потрібно архівувати
      5   * @param now - момент часу для позначки архівування
      6   * @returns оновлену задачу зі станом archived
      7   * @throws TaskNotFoundError якщо задачі немає у сховищі
      8   * @example
      9   * const archived = archiveTask(task, new Date());
     10   */
     11  export function archiveTask(
     12    task: Task, now: Date,
     13  ): Task { /* ... */ }

  Між JSDoc і TSDoc існує принципова відмінність. У JavaScript типів немає,
тому їх зазначають у коментарі: @param {string} name. У TypeScript тип уже
присутній у сигнатурі, і дублювання його в коментарі створює два джерела
правди, які неминуче розійдуться. Натомість тег @throws у TypeScript
незамінний: мова не має перевірюваних винятків, і з сигнатури функції
неможливо дізнатися, які помилки вона може породити.
  Документувати слід публічний інтерфейс модуля або пакета – те, що викликають
ззовні. Приватна функція обсягом у кілька рядків із промовистою назвою
документаційного коментаря не потребує.

3.7 Конвенції стилю кодування для конкретних мов

  Конвенції відрізняються між мовами: вони формувалися різними спільнотами й у
різний час. Нижче наведено огляд конвенцій найпоширеніших мов.

Мова        | Стандарт стилю          | Характерна особливість
------------+-------------------------+-----------------------------------------
Python      | PEP 8, PEP 257          | відступи є частиною синтаксису; імена у
            |                         | snake_case
Java        | Oracle Code Conventions | один публічний клас на файл; методи у
            |                         | camelCase
C++         | єдиного стандарту немає | власні стайлгайди компаній: Google,
            |                         | LLVM, Mozilla
JavaScript  | офіційного стандарту    | де-факто: Airbnb Style Guide, усталення
            | немає                   | Prettier
TypeScript  | Google TypeScript Style | частина правил задається у файлі
            | Guide                   | tsconfig.json

  Для перевірки дотримання стилю використовують два різні класи інструментів.
Форматер приводить код до єдиного вигляду, переписуючи його; лінтер аналізує
код і повідомляє про підозрілі конструкції, не змінюючи вигляд.

Інструмент  | Мова                   | Призначення
------------+------------------------+----------------------------------------
Prettier    | JavaScript,            | форматер: друкує код заново за єдиними
            | TypeScript, CSS        | правилами
ESLint      | JavaScript, TypeScript | лінтер: виявляє відомі проблемні
            |                        | конструкції
Pylint,     | Python                 | перевірка відповідності PEP 8 і типових
Ruff        |                        | дефектів
ClangFormat | C, C++                 | форматер за обраним стайлгайдом
            |                        | (Google, LLVM)
Checkstyle  | Java                   | перевірка відповідності стандарту
            |                        | оформлення

  Мова TypeScript має особливість, якої немає в більшості мов: частина її
конвенцій перевіряється компілятором, оскільки задається у файлі конфігурації
tsconfig.json. Причина полягає в тому, що типи TypeScript стираються під час
компіляції – у згенерованому JavaScript їх немає. Отже, усе, що описано
типами, перевіряється до запуску програми, а дані, які надходять ззовні, не
перевіряються взагалі.
      1  {
      2    "compilerOptions": {
      3      "strict": true,              // null, undefined - окремі типи
      4      "noUncheckedIndexedAccess": true,   // arr[0]: T | undefined
      5      "noImplicitReturns": true,   // гілки повертають значення
      6      "erasableSyntaxOnly": true   // лише те, що стирається
      7    }
      8  }

  Без увімкненого режиму strict значення null і undefined належать до будь-
якого типу, тобто оголошення string фактично означає «рядок, або null, або
undefined». Анотація типу в такому разі перестає бути гарантією. Тому файл
tsconfig.json слід розглядати як частину правил оформлення коду, а не як
технічну деталь збирання проєкту.

3.8 Кодування на основі тестування (TDD)

  Розробка через тестування (Test-Driven Development) – це підхід, за якого
тест пишеться раніше за код, який він перевіряє. Цикл складається з трьох
кроків.

Крок     | Зміст кроку
---------+-----------------------------------------------------------------
Red      | пишеться тест на ще не реалізовану поведінку; тест не проходить
Green    | пишеться мінімальний обсяг коду, достатній для проходження тесту
Refactor | код упорядковується; тест підтверджує, що поведінка не змінилася

  Вплив підходу на оформлення коду є безпосереднім. Тест змушує спочатку
сформулювати очікуваний результат і лише потім – спосіб його досягнення. Крім
того, код, написаний під тест, має меншу зв’язність: щоб функцію можна було
викликати ізольовано, вона не повинна залежати від глобального стану та
побічних ефектів.
  Зв’язок із рефакторингом є визначальним. Рефакторинг за означенням М.
Фаулера – це зміна внутрішньої структури коду без зміни його зовнішньої
поведінки. Підтвердити незмінність поведінки можна лише тестами; без них зміна
структури є переписуванням навмання.
  Тести є програмним кодом, тому правила оформлення поширюються на них
повністю. Усталені підходи, що полегшують подальшу підтримку:
      1  test('archiveTask позначає задачу як архівовану', () => {
      2    const task = makeTask({ status: 'active' });   // Arrange
      3    const result = archiveTask(task, FIXED_DATE);  // Act
      4    expect(result.status).toBe('archived');        // Assert
      5  });

  – назва тесту формулюється як речення про поведінку, а не як назва методу,
що перевіряється;
  – структура тесту відповідає схемі AAA (Arrange – Act – Assert) і видима з
першого погляду;
  – один тест перевіряє одну поведінку, інакше за фактом невдачі неможливо
визначити, що саме порушено;
  – тест має бути відтворюваним: замість поточного часу використовується
фіксоване значення, інакше тест падатиме випадково.

3.9 Інструменти та автоматизація для підтримки якості коду

  Конвенція, дотримання якої не перевіряється автоматично, із часом перестає
виконуватися. Тому перевірки вбудовують у процес розробки на кількох рівнях,
що відрізняються швидкістю та повнотою.

Рівень      | Інструменти        | Момент спрацьовування
------------+--------------------+-------------------------------------------
Редактор    | Prettier, ESLint   | під час набору тексту та збереження файлу
Git Hooks   | husky, lint-staged | перед комітом, лише для змінених файлів
CI/CD       | GitHub Actions,    | на кожне надсилання змін: перевірка всього
            | GitLab CI          | проєкту і тести
Статичний   | SonarQube, Codacy  | дублювання, складність, покриття тестами,
аналіз      |                    | динаміка якості

  Git Hooks – це механізм системи контролю версій, який дозволяє запускати
сценарії на певних подіях. Засіб husky налаштовує такі сценарії, а lint-staged
обмежує перевірку лише файлами, доданими до поточного коміту, завдяки чому
перевірка триває секунди, а не хвилини.
  Системи неперервної інтеграції (CI/CD) виконують повну перевірку проєкту на
сервері: форматування, лінтер, перевірку типів і запуск тестів. Невдала
перевірка блокує злиття змін, тому порушення конвенції фізично не потрапляє до
основної гілки.
  Платформи статичного аналізу SonarQube та Codacy працюють на вищому рівні:
вони оцінюють проєкт загалом – обсяг дублювання, цикломатичну складність,
покриття тестами – і відстежують зміну цих показників у часі. Це дозволяє
виявляти накопичення технічного боргу, яке непомітне під час перегляду окремої
зміни.
  Для мови TypeScript окремо слід зазначити команду перевірки типів tsc
--noEmit: це єдиний інструмент, який аналізує проєкт наскрізь. Зміна типу в
одному файлі спричиняє помилки в усіх місцях, де цей тип використовується, –
ані форматер, ані лінтер такої перевірки не виконують.

3.10 Приклади оформлення коду: аналіз та обговорення

  Нижче наведено фрагмент коду, що порушує більшість розглянутих правил, та
його варіант після застосування конвенції. Повні тексти обох фрагментів
наведено в додатку В.
      1  function pr(d:any){
      2  let r=[];
      3  for(let i=0;i<d.length;i++){
      4  // перевірка
      5  if(d[i].s==2&&Date.now()-d[i].c>86400000)
      6  r.push(d[i]);}
      7  return r;}

  Виявлені недоліки: імена pr, d, r, s, c не передають змісту; тип any вимикає
перевірку типів для всієї гілки коду; число 86400000 і код стану 2 є магічними
значеннями; коментар «перевірка» переказує код і не додає інформації;
відсутність форматування ускладнює читання; оператор нестрогого порівняння ==
виконує неявне перетворення типів.
      1  const DAY_MS = 24 * 60 * 60 * 1000;
      2
      3  /** Повертає задачі, завершені понад добу тому. */
      4  export function findStaleDone(
      5    tasks: Task[], now: number,
      6  ): Task[] {
      7    return tasks.filter(
      8      (task) =>
      9        task.status === 'done' && now - task.createdAt > DAY_MS,
     10    );
     11  }

  Застосовані правила: описові імена замість скорочень; іменована константа
замість магічного числа; літеральний тип стану замість числового коду;
конкретні типи замість any; документаційний коментар замість коментаря-
переказу; форматування, виконане автоматично.
  Вплив чистоти коду на роботу команди проявляється у кількох напрямах. Під
час рев’ю обговорюється логіка, а не розставлення пробілів. Новий розробник
читає код як зв’язний текст, а не розшифровує його. Пошук дефекту
скорочується, оскільки зрозумілий код дає коротший шлях від симптому до
причини. Зникають конфлікти злиття, спричинені різним форматуванням. Нарешті,
технічний борг не накопичується непомітно, бо автоматичні перевірки не
дозволяють внести його до основної гілки.
  Отже, чистота коду є не естетичною, а економічною категорією: вона зменшує
вартість кожної наступної зміни в проєкті.

4 ВИСНОВКИ

  Було розглянуто правила оформлення програмного коду як узгоджений набір
домовленостей, що охоплює структуру проєкту, форматування, іменування,
коментарі, документування та тестування.
  Було встановлено, що потреба в конвенції випливає зі співвідношення між
написанням і читанням коду: фрагмент пишеться один раз, а читається
багаторазово, тому оптимізувати слід саме читання. Основними перевагами
дотримання стилю визначено читабельність, підтримуваність, мінімізацію помилок
і чистоту змін у системі контролю версій.
  Було з’ясовано, що правила відрізняються між мовами програмування, проте
принцип залишається спільним: єдність у межах проєкту важливіша за вибір
конкретного правила. Для мови TypeScript виявлено особливість, якої немає в
більшості мов, – частина конвенцій задається у файлі tsconfig.json і
перевіряється компілятором, а не лише домовленістю між розробниками.
  Було проаналізовано інструменти підтримки якості коду та визначено розподіл
їхніх ролей: форматер відповідає за вигляд коду, лінтер – за виявлення відомих
проблемних конструкцій, перевірка типів – за узгодженість проєкту загалом,
платформи статичного аналізу – за динаміку якості в часі.
  Отримано навички аналізу програмного коду на відповідність конвенції,
виявлення типових порушень та їх усунення, а також навички налаштування
автоматичних перевірок на рівні редактора, Git Hooks і системи неперервної
інтеграції.
  На підставі опрацьованого матеріалу сформульовано практичну рекомендацію:
впровадження конвенції доцільно починати не з написання документа з правилами,
а з трьох файлів у репозиторії – .editorconfig, конфігурації форматера та
конфігурації лінтера – і з під’єднання цих перевірок до Git Hook та конвеєра
CI. Правило, дотримання якого перевіряє машина, виконується завжди; правило,
записане лише в документі, із часом порушується.

      1  /**
      2   * Служба роботи із задачами.
      3   * Усі публічні функції документовані у форматі TSDoc.
      4   */
      5  import { Task, TaskStatus } from '../shared/types/task';
      6
      7  /** Кількість мілісекунд в одній добі. */
      8  const DAY_MS = 24 * 60 * 60 * 1000;
      9
     10  /**
     11   * Повертає задачі, завершені понад добу тому.
     12   *
     13   * @param tasks - перелік задач для перевірки
     14   * @param now - поточний момент часу в мілісекундах
     15   * @returns задачі зі станом done, завершені понад добу тому
     16   */
     17  export function findStaleDone(
     18    tasks: Task[], now: number,
     19  ): Task[] {
     20    return tasks.filter(
     21      (task) =>
     22        task.status === TaskStatus.Done &&
     23        now - task.completedAt > DAY_MS,
     24    );
     25  }
     26
     27  /**
     28   * Архівує задачу та прибирає її зі списку активних.
     29   *
     30   * @param task - задача, яку потрібно архівувати
     31   * @param now - момент часу для позначки архівування
     32   * @returns оновлену задачу зі станом archived
     33   * @throws TaskNotFoundError якщо задачі немає у сховищі
     34   */
     35  export function archiveTask(task: Task, now: Date): Task {
     36    if (!task) {
     37      throw new TaskNotFoundError('Задачу не знайдено у сховищі');
     38    }
     39    return {
     40      ...task, status: TaskStatus.Archived, archivedAt: now,
     41    };
     42  }
